## Tables

| Table | What a row means |
|---|---|
| `ingestion_runs` | One run of a job: status (`running`, `succeeded`, `partial`, `failed`), start and finish times, stored input (`input_evidence_version_id`), data version, row counts (seen / inserted / updated / unchanged / rejected), `last_committed_row`, and for a retry the run it retries and where it resumed. |
| `ingestion_errors` | Each rejected row or failure: stage (`parse`, `validate`, `write`, `run`), code, message, row number and key, field, and the raw row (left out if it looks like it contains a secret). |
| `validation_results` | Per run and rule: severity, rows checked, rows failed. |
| `data_versions` | Each distinct content of a dataset gets version 1, 2, 3 …, tied to the stored file. Re-importing identical content reuses the version. |
| `ingestion_cursors` | Where a job continues next time (for files, the last data version; for APIs, a page token or date). |

## How a run works

1. The run row is committed first, so a crash still leaves a record.
2. The raw input is stored as evidence (17.7) and gets a data version.
3. Each row is checked against the job's rules. `error` rules reject the row with a reason; `warning` rules are counted but the row is kept. Duplicate keys within one file are rejected.
4. Rows are written in batches. Each row runs in a savepoint, so one bad row can't break the batch. Each batch commits and moves `last_committed_row`.
5. The run ends `succeeded`, or `partial` if any rows were rejected. A run-level problem (database error, `TransientError` such as a 429 from a source) marks it `failed`.
6. `retry_import` reloads the stored input. A failed run resumes after its last committed row; any other run is reprocessed from the start, which is safe because writes are idempotent.

## Writing a job

Subclass `Job`, set `name`, `dataset_key`, `source` (a `SourceSpec`), `rules`, and implement:

* `parse(content) -> Iterable[InputRow]`: give each row a stable key (for example the CIK).
* `write(ctx) -> "inserted" | "updated" | "unchanged"`: look records up before inserting so repeats don't duplicate; raise `RowRejected(code, message)` to reject a row; call `ctx.cite(record)` to link the stored input as evidence.

## The 200-company seed import

`SeedCompaniesJob` loads the project's research list (CSV export). Per row it creates or updates the company, the SEC issuer as a legal entity, CIK and ticker identifiers (ticker scoped to its exchange), GICS/ICB sector and sub-industry, the project sector group, index memberships observed on the check date, and the issuer name as an alias. A changed issuer name keeps the old one as a `former_name` alias.

* Values are marked `unverified`: the list is a compilation, not a check against SEC or index providers.
* "No" in an index column is not stored. One check is not proof of non-membership.
* Filing dates and research notes are not modelled yet; they remain in the stored CSV.

```bash
python -m cyber_risk_intelligence.ingest run seed-companies path/to/companies-200-seed.csv
python -m cyber_risk_intelligence.ingest retry seed-companies <run id>
```

Exit code 0 means succeeded, 2 partial (rejected rows are printed), 1 failed.
