# 11.2 Infostealer exposure (aggregate counts per company domain)

`python -m cyber_risk_intelligence.breaches infostealers [--limit N]`
`python -m cyber_risk_intelligence.breaches infostealer-summary`

Infostealers are malware that copy saved browser logins from an infected computer, often a personal
or contractor device. [Hudson Rock](https://www.hudsonrock.com/free-tools) offers a free, keyless
domain search over its database of infected computers (about 37 million). For a domain, it reports how
many infected computers had saved logins for:

* **employees**: the company's own staff login pages (SSO, VPN, webmail ...),
* **users**: the company's customer login pages,
* **third parties**: other services tied to the domain,

along with the dates of the latest infections, malware families and a password-strength breakdown.

## What a run does

* Asks for every current company domain, one at a time with a 2-second pause (about 9 minutes for
  215 domains). `--limit N` asks only the first N, for a trial run.
* Keeps a **redacted summary** only: counts, dates, family and password-strength tallies, and the
  **host names** of login pages with their counts (`vpn.acme.com`: 12). URL paths and queries, user
  names, email addresses and anything containing `@` are dropped before storage. The summary is what
  is stored as evidence. No password, cookie or credential is ever kept.
* A rate limit (429) or server error is retried 3 times, then recorded as `lookup_failed` with **no
  counts** (never zero) and asked again next run. Any other HTTP error, or an answer that isn't the
  expected JSON, is also `lookup_failed`.
* An answer with all counts at 0 is `none_reported`: Hudson Rock has no infection for the domain, which
  is not proof there was none.
* Each run adds rows, so history is kept.

## Tables

| table / view | what it holds |
|---|---|
| `aggregate_exposure_observations` | One row per company domain per run: `provider` (hudson_rock), `outcome` (found / none_reported / lookup_failed), `message`, `total_infections`, `employees`, `users`, `third_parties`, `last_employee_infection_at`, `last_user_infection_at`, `stealer_families`, `employee_password_strength` / `user_password_strength` (quantities per strength level), `employee_login_hosts` (host, occurrence, hint: remote_access / identity / mail), `third_party_domains`, `source_dataset_size`, `observed_at`, `evidence_version_id`, `ingestion_run_id`. Checks: a failed lookup has no counts, and an answer has evidence. |
| `latest_aggregate_exposure` (view) | The newest answered row per domain and provider. Failed lookups are skipped so they never hide the last real answer. |

## Rules and limits

* **A lead, not a breach.** A count says that infected computers saved logins for the company's pages.
  It doesn't say the company was breached or that the logins still work. It's a question for the
  company: do they reset passwords, require MFA and revoke sessions for exposed staff?
* **Terms.** Hudson Rock's terms of service grant no licence to reuse its content without permission.
  This is used for internal underwriting research only: counts kept with source and date, not
  republished. For wider use, ask Hudson Rock or use their API under its own terms.
* **Missing stays missing.** `lookup_failed` is unknown, and `none_reported` is "not in this source".
