# 27.7 Data quality validation

Migration: `migrations/versions/0004_validation_runs.py`
Models: `src/cyber_risk_intelligence/models/quality.py`
Code: `src/cyber_risk_intelligence/quality/`

## Running it

```bash
python -m cyber_risk_intelligence.quality             # schema and data checks
python -m cyber_risk_intelligence.quality --evidence  # also re-hash every stored evidence file
```

Exit code 0 means passed or warnings only, 1 means an error-level check failed, and 2 means a check could not run. Run it after every import.

## Tables

| Table | What a row means |
|---|---|
| `validation_runs` | One run of the suite: status (`passed`, `warnings`, `failed`, `error`), times, how many checks ran, and how many found errors or warnings. |
| `validation_results` | Per check: severity, rows checked, rows failed, and a description of what the check means and how it treats unknown values. Shared with 17.8; each row belongs to exactly one import run or validation run. |
| `validation_findings` | Each affected record (table and id) with the reason. There's no foreign key, so findings stay readable after the record is fixed or deleted. |

## Checks

| Check | Severity | Finds |
|---|---|---|
| constraints_validated | error | constraints left `NOT VALID` |
| valid_period_order | error | `valid_to` not after `valid_from` |
| duplicate_active_identifier | error | the same normalized identifier active twice at once |
| duplicate_active_relationship | error | overlapping copies of the same relationship |
| ownership_cycle | error | two entities that are each other's parent in the same period |
| date_in_future | error | past-tense dates (valid_from, observed, published, archive capture, index check) after today |
| archive_capture_after_collection | error | an archive copy captured after we collected it |
| orphan_evidence_link | error | evidence links pointing at missing records |
| verified_without_evidence | error | values marked `verified` with no supporting evidence |
| evidence_bytes_integrity (`--evidence`) | error | stored files that are missing or no longer match their SHA-256 |
| published_after_collection | warning | publication date after collection (usually a "last updated" date) |
| missing_source_reference | warning | collected values with neither a citation nor an evidence link |
| company_without_legal_entity | warning | companies with no legal entity yet |
| possible_duplicate_company | warning | companies with the same normalized name (review only, never auto-merged) |
| unreferenced_evidence_object | warning | stored bytes no capture refers to |
| ingestion_run_stuck | warning | imports still "running" after 6 hours |
| failed_ingestion_not_retried | warning | failed imports with no retry or later success |
| unlinked_legal_entity | info | entities without a company group (allowed: the group is unknown) |

**Unknown is not a failure.** NULL dates, countries or groups never fail a check. Each check's description says how it treats them.

Several error checks repeat what a constraint already enforces. They catch data that got past a missing or `NOT VALID` constraint, and they list each affected record instead of stopping at the first error.

## Adding a check

Add a `Check(name, severity, description, checked_sql, failing_sql)` to `CHECKS` in `quality/checks.py`. `failing_sql` returns `(table_name, record_id, message)`. Add a test that builds a bad row (dropping the guarding constraint inside the test transaction if needed) and asserts the finding.

## Not covered yet

Date precision (for example "known to the month only") has no column yet. It will be checked when a later schema adds one.
