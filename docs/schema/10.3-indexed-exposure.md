# 10.3 Indexed exposure (Shodan InternetDB)

`python -m cyber_risk_intelligence.exposure collect [--side-hosts 40]`
`python -m cyber_risk_intelligence.exposure summary`
`python -m cyber_risk_intelligence.exposure side-hosts`  (which CT names `collect` would pick, per domain; nothing is looked up)

[Shodan InternetDB](https://internetdb.shodan.io/) is a free lookup (no key) of what Shodan's own
scans have indexed for an IP address: open ports, software (CPE), CVEs inferred from those
versions, host names and tags (`cdn`, `cloud` ...). We read Shodan's index; nothing is sent to the
company's hosts or IPs.

## What is looked up

For each company domain:

* the website hosts: the domain, plus `www.` for a registered domain (as in 1.2 and 10.1);
* the domain's MX hosts that sit under one of the company's own domains. A mail host run by a
  provider (Microsoft 365, Proofpoint, Google ...) is skipped, because its IPs serve thousands of
  companies;
* **side hosts** (`host_role = certificate_name`): up to `--side-hosts` (default 40) names per
  domain taken from the company's own certificates in Certificate Transparency logs (10.1,
  `certificate_hostnames`). Only exact names (no wildcards) under the domain, from certificates
  valid within the last year. Names whose labels suggest an internet-facing service go first,
  recorded in `name_hint`:

  | name_hint | example labels |
  |---|---|
  | `remote_access` | vpn, sslvpn, remote, citrix, gateway, rdp, rdweb, vdi, globalprotect, anyconnect |
  | `file_transfer` | ftp, sftp, mft, files, transfer, sharefile |
  | `admin` | admin, manage, mgmt, console, cpanel, ilo, idrac |
  | `mail` | owa, webmail, mail, exchange, smtp, autodiscover |
  | `identity` | sso, adfs, sts, login, auth, idp |
  | `development` | jira, confluence, git, jenkins, dev, test, staging, uat, api |

  The rest follow, most recently certified first. No name is guessed: each comes from a
  certificate the company had issued.

Each host is resolved through public DNS (A records, at most 8 IPs per host), and each IP is
looked up in InternetDB once per run. Nothing is sent to any of the hosts.

## Tables

| table | what it holds |
|---|---|
| `indexed_host_lookups` | One row per (host, IP) per run: `host_role` (website / mail / certificate_name), `name_hint`, `outcome`, `attribution`, Shodan's `tags`, `hostnames`, `cpes`, `potential_vulns`, `source_scan_date`, and the InternetDB answer as evidence. |
| `indexed_service_observations` | One row per indexed port of a found IP: `port`, `service_hint` (from the port number), `sensitive`, `attribution`. |

| outcome | meaning |
|---|---|
| `found` | Shodan has a record for the IP. |
| `not_indexed` | Shodan has no record (InternetDB answered 404). Not "nothing exposed": Shodan may simply not have scanned it. |
| `lookup_failed` | InternetDB didn't answer (timeout, rate limit, server error). Unknown. |
| `dns_failed` / `no_address` | The host didn't resolve (lookup failed / no A record). No IP is stored. |

## Reading the results

The rules from issue 10.3:

* **Shared IP evidence is not ownership.** `attribution` says how far an IP can be tied to the
  company, from Shodan's own tags and host names:
  * `cdn`: a CDN edge (Cloudflare, Akamai, CloudFront ...). Its ports are the CDN's, not the company's.
  * `shared`: the IP also serves other organizations' names (shared hosting, a cloud load balancer).
  * `company_only`: every host name Shodan knows for it is under the company's domains.
  * `unknown`: Shodan knows no host name for it.

  The summary lists ports and CVEs only for `company_only` and `unknown` IPs, and then lists the
  side hosts on those IPs whose name suggests a service, with their ports and software.
* **A banner is not a confirmed vulnerability.** `potential_vulns` are CVEs Shodan infers from
  software version strings. Backports and patches often make them false.
* **Scan dates.** InternetDB doesn't say when Shodan scanned the IP (its data is refreshed
  roughly weekly), so `source_scan_date` is null: unknown, never made up. `retrieved_at` is when we
  asked.
* `sensitive` ports are remote administration, file sharing and database services that should
  rarely face the internet: FTP 21, Telnet 23, RPC 111/135, NetBIOS 139, SNMP 161, LDAP 389,
  SMB 445, rsync 873, MSSQL 1433, Oracle 1521, PPTP 1723, NFS 2049, Docker 2375, MySQL 3306,
  RDP 3389, PostgreSQL 5432, VNC 5900, WinRM 5985/5986, Redis 6379, Elasticsearch 9200,
  Memcached 11211, MongoDB 27017. SSH (22) is recorded but not counted as sensitive.
