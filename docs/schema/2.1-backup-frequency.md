# 2.1 Published backup frequencies

Migrations: `migrations/versions/0011_backup_policy_claims.py`, `0012_csa_star_backup.py`
Model: `src/cyber_risk_intelligence/models/backup.py`
Code: `src/cyber_risk_intelligence/backup/`

`backup_policy_claims` records what a company says on its own pages about how often it backs up,
what, how, and for how long. Every row is the company's own statement, so
`verification_status` is always `claimed`.

## Where rows come from

Rows are read from 1.1 `backup_and_recovery` claims (trust center, security pages, published
documents). The trust-center collector adds them as it collects; `backup derive` backfills them
from claims already stored. One sentence gives one row per schedule it states:
"daily full backups and incremental backups every 4 hours" gives two rows.

The 1.1 extractor now also picks up "back up" as a verb, snapshots and replication.

### Second source: CSA STAR CAIQ self-assessments

Few companies state a schedule on their own pages, and SEC 10-K filings don't either (a full-text
search of the 200 companies' 10-Ks from 2024 onward found no backup schedules). The one other public
source that asks the question in a standard way is the **Cloud Security Alliance STAR Registry**:
cloud providers publish their answers to the CAIQ questionnaire there, including
*BCR-08.1 "Are backups performed periodically?"* with an implementation description.

```bash
python -m cyber_risk_intelligence.ingest run csa-star csa_star_targets.csv
```

The CSV has `company_key,service_name,service_url,caiq_url`, where `caiq_url` is the registry's own
"Download CAIQ Self-assessment" link (only `https://cloudsecurityalliance.org/star/registry/...`
links are accepted). The workbook is fetched (robots.txt obeyed), stored as evidence, and each
answered backup question becomes a row with `basis = 'csa_star_caiq'`, the question id, the answer,
the control ownership and the service name. A CAIQ is still the provider describing itself, so these
rows are `claimed` too.

* The schedule is read from the implementation description. "Backups are performed periodically"
  leaves it unknown.
* A "No" answer is kept as `assertion = 'negated'`; NA or blank answers give no row.
* A control marked `CSC-owned` (the customer's job) is stored as `customer_responsibility`.
* A CAIQ covers the provider's own cloud service. Nothing from it is copied to the provider's customers.

Coverage (November 2026): searching the registry for the 200 companies found 19 providers. 17 of
them publish a CAIQ workbook for 42 services (Alphabet/Google, Accenture, Adobe, Cisco, CrowdStrike,
Datadog, Equinix, Fortinet, IBM, Microsoft, NetApp, Oracle, Palo Alto Networks, Rockwell Automation,
Salesforce, ServiceNow, Workday). Amazon (AWS), Okta and Oracle Cloud Infrastructure publish theirs
only as PDF, which this import does not read yet. Most answers say backups are taken "periodically";
a schedule is stated for Google Looker, Cisco Duo and Secure Email (daily), Microsoft 365 (near-real
time replication), Oracle SaaS (daily/weekly) and ServiceNow (daily differential, weekly full,
14-day retention).

## What each row says

| column | meaning |
|---|---|
| `frequency_class` | `continuous`, `sub_hourly`, `hourly`, `sub_daily`, `daily`, `weekly`, `monthly`, `other`, or **NULL when the sentence gives no schedule** |
| `interval_minutes` | the interval when one is stated (daily = 1440, every 15 minutes = 15). Always NULL for `continuous` |
| `frequency_phrase` | the words the schedule was read from ("nightly", "every 4 hours") |
| `scope` | `own_practice`, `product_capability` ("you can schedule backups hourly"), or `customer_responsibility` ("customers are responsible for backing up") |
| `covered_system` | what is backed up, as the sentence names it ("customer data", "production databases") |
| `methods` | any of full, incremental, differential, snapshot, replication |
| `retention_days`, `rpo_minutes`, `rto_minutes` | when stated, with the phrase they came from |
| `basis` | `company_statement` (own pages, via 1.1) or `csa_star_caiq` (CSA STAR Registry questionnaire) |
| `caiq_question_id`, `caiq_answer`, `control_ownership`, `service_name` | CSA STAR rows: question (e.g. BCR-08.1), yes/no, CSP-owned / shared / CSC-owned, cloud service |
| `quote`, `source_ref`, `evidence_version_id`, `claim_id` | the sentence (or question, answer and description), page or registry URL, stored capture, 1.1 claim |
| `page_updated_on`, `observed_at` | the date the page states, and when we captured it |

## Rules

* **Daily and continuous stay apart.** Continuous replication has no interval; daily is 1440 minutes.
  Neither is turned into the other.
* **Not stated means unknown.** A sentence that mentions backups but gives no schedule is stored
  with `frequency_class` NULL. The `backup_frequency_not_stated` check (info) lists companies whose
  own backup statements never give a schedule.
* **A vendor's product text is not a customer's policy.** Product features and customer duties get
  their own `scope`, so they are not counted as the company's own practice, and nothing is copied to
  the vendor's customers.
* **Test and review schedules are not backup schedules.** "Our disaster recovery plan is tested
  annually" gives no row; "backed up nightly, restores tested quarterly" gives only `daily`.
* Negated statements keep `assertion = 'negated'` and are left out of the view.

## Running it

```bash
alembic upgrade head
python -m cyber_risk_intelligence.backup derive     # backfill from what 1.1 already collected; safe to repeat
python -m cyber_risk_intelligence.backup summary    # per company, scope and frequency
```

The `company_backup_frequencies` view gives one row per company, scope and frequency class with the
number of statements, the systems named, the shortest interval, retention range, best RPO/RTO and
`sources` (which bases the rows came from).
