# 10.1 Certificate Transparency: certificates and hostnames

Migration: `migrations/versions/0013_certificate_transparency.py`
Model: `src/cyber_risk_intelligence/models/certificates.py`
Code: `src/cyber_risk_intelligence/ct/`

Every publicly trusted TLS certificate is written to public Certificate Transparency (CT) logs.
Searching those logs for a company's domains shows which names it has had certificates for:
websites, APIs, test and staging systems. It is passive: **no host named in a certificate is
resolved, contacted or scanned**, and a name in a certificate is not proof that a host is live.

## Sources

1. **Cert Spotter** (SSLMate) search API, first choice. It returns current certificates 100 per
   page in well under a second and is paged with `after=<id>`, so even very large estates can be
   read: in a test, microsoft.com (more than 300,000 current certificates, where crt.sh times out)
   gave 300,000 certificates and about 25,700 Microsoft names in 10 minutes before the page limit. An API key is optional: put `CERTSPOTTER_API_KEY=...` in `.env` for a higher
   allowance (it is sent as a header and never stored). A short rate-limit pause (429)
   is waited out. A long one, which the free allowance gives after a few hundred pages, sends
   domains to crt.sh until the allowance is back, without asking Cert Spotter again. A domain
   crt.sh can't answer either (the very large ones) waits for Cert Spotter, up to an hour.
   `ct collect` runs in two passes. The first pass doesn't wait for a long rate limit: a domain that
   would have to wait is left for later, and the pages it already read are kept. The second pass
   takes those big domains, waits for Cert Spotter and carries on from the page each one reached.
2. **crt.sh**, fallback when Cert Spotter cannot answer. One request per domain, often slow, and
   very large domains time out there.

A search that stops early (a page still failing after retries, or more than `CT_MAX_PAGES` pages,
default 3000 = 300,000 certificates) keeps what was read and is marked `complete = false`. A search
that gets nothing from either source is `lookup_failed`, which means unknown, not "no certificates".

## Running it

```bash
alembic upgrade head
python -m cyber_risk_intelligence.ct collect    # every current company domain
python -m cyber_risk_intelligence.ct summary    # per domain: latest search, certificates, hostnames
# or a chosen list:  python -m cyber_risk_intelligence.ingest run ct targets.csv   (company_key,domain)
```

Each search asks for the domain and its subdomains, current (unexpired) certificates only.
Certificates, names and sightings are written in bulk, so a domain with 100,000 certificates is one
row in the run, not 100,000 round trips.

## Tables

| table | one row per | notes |
|---|---|---|
| `ct_lookups` | search for a domain | `source` (certspotter / crt.sh), `outcome` answered / no_results / lookup_failed, `pages`, `complete`, HTTP status, message, entry and certificate counts; the raw answer is stored as evidence, gzipped JSON (`evidence_version_id`) |
| `certificates` | certificate | identity: `tbs_sha256` (Cert Spotter) or issuer + `serial_number` (crt.sh); issuer, `cert_sha256`, `revoked` as reported, `not_before` / `not_after` (UTC), first/last time we saw it |
| `certificate_observations` | sighting of a certificate in a search | the source's entry id, a public link (crt.sh), evidence version, time |
| `certificate_hostnames` | name a certificate covers | `is_wildcard`, `base_name` (without `*.`), `domain_id` of the known domain it falls under, if any |

**Duplicates collapse.** A precertificate and the final certificate share their to-be-signed hash
(Cert Spotter reports them as one issuance) and their issuer and serial number (crt.sh lists two
entries); either way they become one `certificates` row. The same certificate found through the two
different sources can appear twice, because crt.sh does not give the hash; normally one source is used. Searching again,
or finding the same certificate under another company domain, adds observations, not certificates.

**Wildcards stay patterns.** `*.dev.example.com` is stored with `is_wildcard = true`. It says the
company can serve any name under `dev.example.com`; it is never counted as a host.

**Company links need domain evidence.** A name is tied to a domain only when it is a known domain in
`domains` or a subdomain of one, and to a company only through that domain's current
`company_domains` link (which carries its own source). Other names on the same certificate
(`unrelated.example`) are kept on the certificate but tied to no company. E-mail addresses and IP
addresses in certificates are not stored as hostnames.

## Views

* `latest_ct_lookups`: the most recent search per domain.
* `company_certificate_hostnames`: per company and name: wildcard or not, number of certificates,
  issuers, earliest `not_before`, latest `not_after`, whether a current certificate covers it, and
  when we first and last saw it.

## Checks

* `ct_lookup_failed` (warning): the latest search for a domain failed; run it again later.
* `company_domain_without_ct_lookup` (info): a company domain has never been searched.

## Website certificate (`website_certificate_checks`)

`python -m cyber_risk_intelligence.ct website` records the certificate each company's own website
presents, the one a browser shows under Inspect › Security. The check makes one TLS handshake on port 443
with the known domain and with its `www.` host, and nothing else. No other port is tried, no page is
requested, and no name inside the certificate is followed.

| outcome | meaning |
|---|---|
| `trusted` | The certificate verified against the system's trusted roots and matched the host name. |
| `not_trusted` | A certificate was presented but failed verification. `message` says why: expired, wrong name, unknown issuer. The certificate is still read and stored. |
| `unreachable` | There was no TLS answer (no such host, refused, timeout). This says nothing about the certificate. |

Each check keeps the issuer, subject, SAN names, serial number, validity dates and SHA-256. The PEM is
stored as evidence. `latest_website_certificates` holds the newest check of each host.
`ct website-summary` prints each host's issuer, expiry date and days left.
